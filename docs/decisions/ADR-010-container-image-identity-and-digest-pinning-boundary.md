# ADR-010: Container Image Identity, Local CRI Resolution, and Production Immutability Separation

**Status**: Accepted  
**Date**: 2026-10-12  
**Decision Makers**: Aditya Rathore (FDE Candidate), Antigravity AI  

---

## 1. Context & Problem Statement

In Gate G6, the custom WooCommerce MCP server (`apps/woocommerce-mcp`) was containerized and configured in the Helm chart. The assignment requires reproducible, immutable deployments and warns against using mutable `latest` image tags.

During the initial deployment to our local k3d cluster, the team attempted to pin the image by digest using the Docker image ID generated by `docker build` (e.g. `sha256:d831a5b6b4c3b21c6d930eece6e484c4ccebcbbcdf9bf00ccea98c61eb9fee6a`):
```yaml
upstreams:
  woocommerce:
    image: "urumi-woocommerce-mcp:1.0.0"
    digest: "@sha256:d831a5b6b4c3b21c6d930eece6e484c4ccebcbbcdf9bf00ccea98c61eb9fee6a"
```

This immediately resulted in a Kubernetes deployment failure:
```text
Failed to pull image "urumi-woocommerce-mcp:1.0.0@sha256:d831...": rpc error: code = Unknown desc = failed to pull and unpack image ... manifest unknown: manifest unknown
Error: ErrImagePull / ImagePullBackOff
```

We needed to resolve the exact OCI specification mechanics causing this failure, establish a robust image resolution pattern for local k3d clusters, and maintain strict immutability standards for production releases without conflating local image IDs with registry distribution digests.

---

## 2. Investigation & Technical Findings

Our deep dive into the **OCI Image Specification** and **containerd CRI implementation** revealed a fundamental architectural distinction:

1. **Docker Image Config ID vs. OCI Distribution Manifest Digest**:
   - **Image Config ID (Local Hash)**: When Docker builds an image locally (`docker build`), it generates a SHA-256 hash representing the uncompressed image configuration JSON (environment variables, architecture, layer diff IDs). In our build, this was `sha256:d831a5b6b...`.
   - **OCI Distribution Manifest Digest**: A distribution manifest digest represents the SHA-256 hash of the OCI image manifest JSON that describes the compressed layer tarballs and config descriptors. **This digest is generated exclusively by an OCI container registry when an image is pushed over the wire.**
   - Inspecting the locally built image via `docker inspect urumi-woocommerce-mcp:1.0.0` confirmed:
     ```json
     "RepoDigests": []
     ```
     Because the image had never been pushed to a registry, it possessed **zero distribution digests**.

2. **containerd CRI Resolution Mechanics**:
   - When Kubernetes schedules a pod whose image reference contains `@sha256:<digest>`, containerd bypasses its local cache and issues an HTTP GET to the upstream registry (by default, Docker Hub `docker.io/library/...`) to fetch that exact distribution manifest.
   - Because `urumi-woocommerce-mcp:1.0.0` is an internal image not hosted on Docker Hub, Docker Hub returned `404 Not Found` / `manifest unknown`, triggering `ErrImagePull`.
   - Appending a local Docker config ID to a remote digest reference is an invalid OCI operation.

---

## 3. Decision

We formally decouple **Local CRI Resolution** from **Production Registry Immutability**:

1. **Local Development Profile (`values-local.yaml` & `values.yaml`)**:
   - The MCP image reference is configured with the versioned tag:
     ```yaml
     image: "urumi-woocommerce-mcp:1.0.0"
     digest: ""
     imagePullPolicy: "IfNotPresent"
     ```
   - Workflow: The image is built locally (`docker build -t urumi-woocommerce-mcp:1.0.0 apps/woocommerce-mcp`) and imported directly into the local k3d containerd image store (`k3d image import urumi-woocommerce-mcp:1.0.0 -c urumi`).
   - containerd resolves the image locally from its CRI image cache using the tag, resolving cleanly to Image ID `sha256:d831a5b6b4c3b21c6d930eece6e484c4ccebcbbcdf9bf00ccea98c61eb9fee6a`. Zero network pull errors occur.

2. **Production-Like Profile (`values-prod.yaml`)**:
   - Aligned to reference `urumi-woocommerce-mcp:1.0.0` with `digest: ""` for local rendering tests, avoiding invalid or fake placeholder digests.

3. **Production Deployment Qualification & Governance Gate (`SEC-REG-01`)**:
   - We explicitly declare that the current image configuration is **qualified strictly for local k3d deployment**. It is **not yet production-ready or immutable** for remote multi-node environments.
   - **Mandatory Production Prerequisite**: Before deploying to a production VPS, the team must:
     1. Push the built image to an authenticated container registry (e.g. GitHub Container Registry / Docker Hub).
     2. Capture the actual OCI distribution manifest digest from the registry response.
     3. Pin `values-prod.yaml` to that verified distribution digest (`digest: "@sha256:<registry_digest>"`).
   - This item is logged as a formal, high-severity blocking item (`SEC-REG-01`) in [`security-and-deployment-readiness-register.md`](../phase-3/security-and-deployment-readiness-register.md).

---

## 4. Consequences & Limitations

- **Positive**:
  - Resolves the `ErrImagePull` blocker in local k3d, allowing pods to schedule and reach `Running` immediately.
  - Eliminates the practice of inventing or misusing local Docker config IDs as remote registry digests.
  - Maintains strict architectural honesty: clearly documents that local CRI imported images lack remote distribution digests.
  - Provides a concrete, auditable milestone for Phase 7 (production rollout).
- **Limitations**:
  - A mutable version tag such as `1.0.0` can theoretically be overwritten in a local environment if a developer rebuilds without changing the tag.
  - Multi-node production clusters cannot rely on `k3d image import` and must have registry access.
